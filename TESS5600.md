# TESS 5600 decoder — goal & plan

## Goal

Add a `sensor-ble` decoder for the TE Connectivity M5600/U5600 ("TESS 5600") wireless pressure transducer, following the existing pattern in `devices/`.

## Sources

- Reference app: [tess5600.ts](https://github.com/mhaberler/tess5600-app/blob/main/src/composables/tess5600.ts)
- [Official TE Connectivity M5600/U5600 Software Manual](https://www.ttieurope.com/content/dam/tti-europe/manufacturers/te-connectivity/resources/TE_M5600_U5600_Software_Manual.pdf) (fetched via WebFetch, read as PDF) — authoritative byte-level protocol spec, page 16-17.
- Live GATT discovery + notification capture against a real TESS 5600 unit via **ble-mcp**.

All three agreed on the Data characteristic layout.

## ble-mcp usage

Used the `ble` MCP server (added this session via `claude mcp add ble -- ssh mah@fpc.local ...`) to verify the protocol against real hardware before writing code, instead of trusting the reference app blindly:

- `ble_scan_start` / `ble_scan_get_results` — found two live TESS 5600 units: `C9:69:81:7A:D1:6C`, `C7:86:03:B9:B7:42`. Confirmed advertised service UUID is the **base** UUID `f0000000-0451-4000-b000-000000000000`, not `f000ab30-...` (PRESSURE_SVC) as might be assumed from the service's own UUID.
- `ble_connect` / `ble_discover` — pulled the full GATT table with characteristic properties (read/write/notify flags). This was the key finding: `STATUS_CHAR` (`f000ab3f-...`) and all Device Information/GAP characteristics are **read-only** (no notify), while `DATA_CHAR` and `BATTERY_CHAR` support both read and notify.
- `ble_read` — spot-read `STATUS_CHAR` (`00` = OK), `BATTERY_CHAR` (`6400` = 100%, discharging — 2 bytes, not 1 as the reference app assumed), `DATARATE_CHAR`, and the model string characteristic (`"5600"`).
- `ble_subscribe` / `ble_wait_notification` — captured a live `DATA_CHAR` notification (`48098305000000000000449d3b01`, 14 bytes) and decoded it by hand to cross-check against the manual's byte layout before trusting it in code.
- `ble_unsubscribe` / `ble_disconnect` — clean teardown.

This surfaced a real API gap: `sensor-ble`'s `BleApi` only exposes `write`, no `read`. Since `STATUS_CHAR` and Device Info are read-only on the real device, they are **structurally unreachable** through this library and were excluded from the decoder's scope — this wasn't guessable from the reference app source alone, only from checking real characteristic properties.

## Decisions (via `/grill-me` interview)

1. **Scope**: `DATA_CHAR` (temp/pressure/pMin/pMax) + `BATTERY_CHAR` (level/charging) via `notify[]`. `STATUS_CHAR` and Device Info excluded (read-only, unreachable).
2. **Field naming**: Pa only, no derived psi/bar duplicates — `temperature_C`, `pressure_Pa`, `pressureMin_Pa`, `pressureMax_Pa`, `batteryLevel_percent`, `batteryCharging_dimensionless`.
3. **Device matching**: `serviceUUID` only, using the live-confirmed advertised base UUID `f0000000-0451-4000-b000-000000000000` (more robust than device name, which is user-renamable via GAP characteristic).
4. **Tests**: normal-value case (from live capture), sentinel/error case (`0x7FFF`/`0x7FFFFFFF`), battery case.
5. **start/stop**: no-ops, matching `hrs.js`/`rscs.js` — no vendor start/stop command exists for this device's Data/Battery characteristics.

## Result

- `devices/tess5600.js` created, registered in `main.js`.
- `npm test` passes (3 new tests + all pre-existing decoder tests unaffected).
- Decoder output cross-checked against live sensor capture — exact match.
